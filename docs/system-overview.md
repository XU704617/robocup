# 人形足球系统结构

[返回目录](../README.md)

这是一张帮助读懂队伍代码的概念图，模块名称和接口不是联赛统一规定。HSL 的比赛内容涉及视觉、双足运动、定位、行为与队伍协作；具体实现可从[官方队伍 TDP](https://hsl.robocup.org/qualified-teams/)和[公开软件栈](https://github.com/bit-bots/bitbots_main)对照学习。

```text
相机 / IMU / 关节反馈 ──→ 感知与状态估计 ──→ 世界模型
                                               │
GameController ──→ 比赛状态 ──────────────────→ 行为决策
                                               │
队友消息 ─────────→ 协作信息 ──────────────────┘
                                               ↓
                                      路径 / 步态 / 踢球 / 起身
                                               ↓
                                        机器人执行器与反馈
```

## 顺着一条动作链排查

假设机器人在允许比赛的状态下看见球，却没有踢球。按数据流查：图像里是否有球、检测结果是否有置信度和时间戳、相机坐标能否变换到机器人/场地坐标、定位是否可信、行为状态机是否选择“接近球”、运动控制是否接受目标、执行器是否完成动作。不要只因“画面里能看到球”就判断感知系统正常。

| 模块 | 典型输入与输出 | 最小测试问题 |
| --- | --- | --- |
| 感知 | 图像、相机标定 → 球/球门/场线/机器人观测 | 光照、遮挡或运动模糊时是否仍能给出可信结果？ |
| 定位与世界模型 | 观测、IMU、里程计、场地模型 → 自身和目标位置 | 坐标系、时间戳与置信度是否一致？ |
| 行为决策 | 比赛状态、目标、队友信息 → 当前任务与动作意图 | 状态变化或通信中断时会做什么？ |
| 运动控制 | 目标速度、脚步或轨迹 → 关节命令 | 起步、摔倒、恢复和急停是否被测试？ |
| 通信与日志 | GameController、队友消息、状态报告 → 有效比赛状态与调试记录 | 是否使用当前协议、队伍编号和正确网络？ |

这张表是调试框架，指标要由队伍设备、项目与当届规则确定。一个有用的测试记录应同时包含输入样本、软件提交号、机器人/仿真平台、运行命令和输出。若结果只在某个光照或场地有效，也应如实注明。

## GameController 是什么位置

GameController 由比赛工作人员操作，通过网络向机器人发布比赛状态。机器人软件需要把这些状态纳入行为逻辑；它自身仍要完成感知、决策和运动。[HSL GameController README](https://github.com/RoboCup-HumanoidSoccerLeague/GameController)说明其配置、协议头文件、状态消息、回传消息和日志位置。[首次运行](first-run.md)用它做无需机器人硬件的入门练习。

## 从 TDP 看不同方案

[Hamburg Bit-Bots 的公开仓库](https://github.com/bit-bots/bitbots_main)展示 ROS 2 模块化实现；[BigHeroX 2026 TDP](https://hsl.robocup.org/wp-content/uploads/2026/03/BigHeroX-tdp-697b35e3beeb6.pdf)描述了感知、双足控制、通信和决策链路。TDP 是队伍自述，适合学习系统设计；性能结论要另看公开实验或[官方比赛结果](https://hsl.robocup.org/results-2026/)。
